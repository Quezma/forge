# Architecture patterns rule catalogue

Cite IDs in findings. Project conventions override these. Stack stays out of scope (see SKILL.md Hard Rules).
Line format: `ID (severity) rule. Check: <probe>. Src: <url> [tag]`. Severity: `blocker` | `major` | `minor`. Tags: `[doc]` primary source fetched while writing this catalogue; `[3p]` third-party/opinion or secondary summary; `[unverified]` URL not fetched or claim not confirmed against it.
A rule applies only when its precondition exists (e.g. RES rules need a remote call, TXN rules need a DB write). Patterns are recommended only for an observed need; absent need, report nothing.

## Layer dependency matrix (from row may depend on column)
| From \ To | presentation/adapters-in | application | domain | infrastructure/adapters-out |
|---|---|---|---|---|
| presentation (controller, handler, CLI, consumer) | yes | yes | DTO/types only | no |
| application (use cases, ports) | no | yes | yes | no (via port) |
| domain (entities, value objects, domain services, events) | no | no | yes | no |
| infrastructure (repositories, ORM models, clients, port impls) | no | yes (ports only) | yes | yes |

Composition root (main/module/bootstrap) is the only place that wires ports to adapters. Cross-feature access goes through the other feature's public API only. Matrix is a clean/hexagonal convention; if the project uses other layer names, map them.

## ARC - architecture and layering
- ARC-01 (major) Source dependencies point inward: domain/application never import infrastructure, framework, or transport types. Check: imports in domain/application of ORM, HTTP, framework, SDK packages. Src: https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html [doc]
- ARC-02 (major) Data crossing a boundary is a plain structure shaped for the inner side, not an ORM row or framework object. Check: entities/ORM models returned from controllers or passed into use cases. Src: https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html [doc]
- ARC-03 (major) Ports (interfaces owned by the application) isolate the core from DBs, queues, and third-party APIs; adapters translate. Check: use cases calling a concrete client/ORM instead of a port. Src: https://alistair.cockburn.us/hexagonal-architecture/ [doc]
- ARC-04 (minor) Feature-first structure: top-level structure tells readers about the system (its use cases/capabilities), not the framework or technical type. Check: tree is `controllers/ services/ models/` only. Src: https://blog.cleancoder.com/uncle-bob/screaming-architecture.html [3p]
- ARC-05 (major) Domain code is free of IO and framework annotations; it is testable with no container, DB, or network. Check: domain tests need mocks of infrastructure; domain imports `fs`, `http`, ORM decorators. Src: https://alistair.cockburn.us/hexagonal-architecture/ [doc]
- ARC-06 (major) One composition root wires dependencies; no service locators or `new ConcreteAdapter()` inside use cases. Check: grep `new .*Repository(`, `container.get(`, global singletons in application code. Src: https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html [3p]
- ARC-07 (minor) Layering is applied where the domain has real rules; thin CRUD may stay a single layer. Check: ceremony (ports, mappers) around a table with no rules. Src: https://martinfowler.com/bliki/AnemicDomainModel.html [3p]
- ARC-08 (major) No import cycles between features/packages; shared code lives in a lower layer. Check: cycle tool, or A imports B and B imports A. Src: https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html [3p]

## DDD - domain modelling
- DDD-01 (major) Bounded contexts: each context owns its model and language; the same word may mean different things; contexts are mapped explicitly. Check: one shared `Customer` model used by billing, support, shipping. Src: https://martinfowler.com/bliki/BoundedContext.html [doc]
- DDD-02 (major) Aggregate = consistency boundary; outside code goes through the root. Check: code mutating child entities without the root. Src: https://martinfowler.com/bliki/DDD_Aggregate.html [doc]
- DDD-03 (major) One aggregate per transaction; "transactions should not cross aggregate boundaries". Check: a single DB transaction saving two aggregate roots. Src: https://martinfowler.com/bliki/DDD_Aggregate.html [doc]
- DDD-04 (major) Aggregates reference other aggregates by ID, not by object; cross-aggregate rules are eventually consistent (events/process). Check: entity fields typed as another root. Src: https://www.dddcommunity.org/wp-content/uploads/files/pdf_articles/Vernon_2011_2.pdf [3p]
- DDD-05 (minor) Value objects are immutable and compared by value; replace common primitives (money, ids, email) with value objects. Check: raw `string`/`number` for domain concepts with rules. Src: https://martinfowler.com/bliki/ValueObject.html [3p]
- DDD-06 (major) Business rules live in domain objects; services only coordinate. Anemic = data bags plus rule-heavy services. Check: entities with only getters/setters, services with `if` chains on entity state. Src: https://martinfowler.com/bliki/AnemicDomainModel.html [doc]
- DDD-07 (major) Anti-corruption layer translates foreign or legacy models at the boundary; foreign types never enter the domain. Check: third-party/legacy DTOs referenced in domain. Src: https://learn.microsoft.com/en-us/azure/architecture/patterns/anti-corruption-layer [doc]
- DDD-08 (minor) Domain events are named in past tense, immutable, raised by the aggregate, and published through the outbox when they leave the process. Check: events named as commands; publish inline in the domain. Src: https://microservices.io/patterns/data/transactional-outbox.html [3p]

## DES - design patterns and SOLID
- DES-01 (minor) A pattern must answer a present need (no patterns where basic code suffices): strategy for 2+ real variants, adapter for a foreign interface, factory for non-trivial construction, decorator for stackable cross-cutting behaviour, repository for aggregate persistence. Check: pattern with one variant and no stated reason. Src: https://refactoring.guru/design-patterns/criticism [3p]
- DES-02 (minor) No presumptive abstraction: build abstractions for current requirements; an interface with exactly one implementation needs a stated reason (e.g. a port at an external boundary or a test seam). Check: `IFoo`/`FooImpl` pairs inside one layer. Src: https://martinfowler.com/bliki/Yagni.html [3p]
- DES-03 (major) No god service: a class with unrelated responsibilities is split by reason to change. Check: constructor parameter count, unrelated method groups. Src: https://blog.cleancoder.com/uncle-bob/2014/05/08/SingleReponsibilityPrinciple.html [3p]
- DES-04 (major) Services do not leak rules out of the domain (anemic CRUD with rules in controllers/handlers). Check: validation and state transitions in controllers. Src: https://martinfowler.com/bliki/AnemicDomainModel.html [doc]
- DES-05 (minor) Prefer composition over inheritance; where inheriting, subclasses must be substitutable. Check: deep hierarchies, overridden methods throwing "not supported". Src: https://en.wikipedia.org/wiki/Composition_over_inheritance [3p]
- DES-06 (minor) Depend on abstractions at layer edges only (DIP); do not abstract stable stdlib or value types. Check: wrappers around `Date`, `Math`, `Array`. Src: https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html [3p]

## MSV - microservices
- MSV-01 (major) Monolith first: split into services only for stated forces (independent deploy/scale cadence, team ownership, fault isolation, differing tech needs). Check: new service/repo with no recorded reason in the ADR. Src: https://martinfowler.com/bliki/MonolithFirst.html [doc]
- MSV-02 (blocker) Database per service: a service's data is private and reached only through its API; no shared DB or shared tables between services. Check: two services' connection strings point at the same schema; one service queries another's tables. Src: https://microservices.io/patterns/data/database-per-service.html [doc]
- MSV-03 (major) Decompose by business capability/subdomain, aligned with team ownership, not by technical layer. Check: services named `data-service`, `validation-service`. Src: https://microservices.io/patterns/microservices.html [doc]
- MSV-04 (major) No distributed monolith: avoid tight runtime coupling (long sync call chains, services unusable alone) and design-time coupling (lockstep releases, shared domain library with rules). Check: request path crossing 3+ services synchronously; services deployed together. Src: https://microservices.io/patterns/microservices.html [doc]
- MSV-05 (minor) API gateway/BFF is the single client entry point for routing/aggregation; business rules stay in services. Check: rules in the gateway; clients calling many services directly. Src: https://microservices.io/patterns/apigateway.html [doc]
- MSV-06 (major) Prefer asynchronous messaging between services to avoid tight runtime coupling; use sync request/response only when the caller needs the answer now. Check: sync call used to propagate a state change that could be an event. Src: https://microservices.io/patterns/communication-style/messaging.html [3p]
- MSV-07 (major) Contracts are versioned and backward compatible; consumers are tested against provider contracts (consumer-driven contracts). Check: breaking field removal/rename in a public API or event; no contract tests. Src: https://martinfowler.com/articles/consumerDrivenContracts.html [3p]
- MSV-08 (minor) Use service discovery (registry/router) instead of hard-coded host/port of peer services, since instance locations change dynamically. Check: grep literal hosts/IPs/ports in clients. Src: https://microservices.io/patterns/server-side-discovery.html [3p]
- MSV-09 (major) Observability baseline per service: a unique request/correlation ID assigned at the edge, passed to every service involved and included in all log messages (distributed tracing). Check: outbound clients/publishers not forwarding trace headers. Src: https://microservices.io/patterns/observability/distributed-tracing.html [3p]
- MSV-10 (major) Health endpoints: liveness is shallow (process only); readiness checks required dependencies with bounded timeouts; optional dependencies excluded. Check: liveness querying the DB; no readiness endpoint. Src: https://learn.microsoft.com/en-us/azure/architecture/patterns/health-endpoint-monitoring [doc]

## RES - resilience
- RES-01 (blocker) Every remote call (HTTP, gRPC, DB, cache, queue) has an explicit timeout (connect and request) and is cancellable. Check: `fetch(`, `axios`, HTTP/DB clients without timeout/`AbortSignal`/deadline. Src: https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter [doc]
- RES-02 (major) Retry only transient failures (timeouts, 5xx, 429, connection reset) of idempotent operations; never retry validation/4xx/business errors. Check: catch-all retry; retry wrapped around non-idempotent POST. Src: https://learn.microsoft.com/en-us/azure/architecture/patterns/retry [doc]
- RES-03 (major) Retries use capped exponential backoff with jitter and a max attempt count; no immediate tight-loop retries. Check: `retry` helper without delay/jitter/cap; `while(true)` + catch. Src: https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter [doc]
- RES-04 (major) No retry amplification: retry at one layer of the stack (or use a local retry budget/token bucket); lower layers fail fast. Check: retries in client lib plus caller plus job runner for the same call. Src: https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter [doc]
- RES-05 (blocker) A non-idempotent operation is never retried (client, queue redelivery, scheduler) unless it carries an idempotency key. Check: retry/redelivery path reaching a create/charge/send without IDM-01/IDM-03. Src: https://learn.microsoft.com/en-us/azure/architecture/patterns/retry [doc]
- RES-06 (major) Circuit breaker (closed/open/half-open) wraps calls to a dependency that can fail for long periods, when sustained failure was observed or is credible; the caller handles the open state; state changes are logged/metered. Check: breaker without fallback/error handling; one breaker over independent shards. Src: https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker [doc]
- RES-07 (minor) Do not add a breaker for local resources, in place of business error handling, or on message consumers that already use DLQ + retry. Check: breaker around in-memory call or queue consumer. Src: https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker [doc]
- RES-08 (major) Bulkhead: isolate pools (connections, threads, queues) per dependency or consumer class so one failing dependency cannot exhaust shared resources. Check: one shared HTTP/DB pool for critical and best-effort calls. Src: https://learn.microsoft.com/en-us/azure/architecture/patterns/bulkhead [doc]
- RES-09 (major) Rate limiting/load shedding at ingress and toward throttled dependencies; honor 429 and `Retry-After`; bounded queues. Check: unbounded queues/concurrency; ignoring `Retry-After`. Src: https://learn.microsoft.com/en-us/azure/architecture/patterns/rate-limiting-pattern [doc]
- RES-10 (major) Fallback/degradation is explicit, tested, and exercised regularly; do not fall back to a path that moves all load onto a weaker dependency. Check: untested `catch` returning stale/default data; cache-miss fallback straight to the DB under failure. Src: https://builder.aws.com/content/3EuS9Sakq7L3VLQIF3qzfMfke1Y/avoiding-fallback-in-distributed-systems [doc]
- RES-11 (minor) Log early retry attempts as info and only the final failure as error; alert on retry-rate spikes. Check: error log per attempt. Src: https://learn.microsoft.com/en-us/azure/architecture/patterns/retry [doc]
- RES-12 (major) Graceful shutdown: stop accepting work, drain in-flight requests/messages, then exit. Check: no SIGTERM handler. Src: https://12factor.net/disposability [doc]

## IDM - idempotency
- IDM-01 (blocker) Mutating endpoints that clients may retry (payments, orders, sends, creates) accept a client-supplied idempotency key. Check: POST creating money/resources without `Idempotency-Key` or equivalent. Src: https://docs.stripe.com/api/idempotent_requests [doc]
- IDM-02 (major) Key semantics: key scoped per client/tenant and operation; first outcome (status and body, including failures after execution began) stored and replayed; same key with different payload is an error; TTL (Stripe v1 prunes after 24h) documented. Check: payload hash compared; stored response; TTL. Src: https://docs.stripe.com/api/idempotent_requests [doc]
- IDM-03 (blocker) Message consumers are idempotent: dedupe on message ID in the same DB transaction as the effect (unique `(consumer, message_id)`), or make the effect naturally idempotent. Check: handler with side effects and no dedup/natural idempotency. Src: https://microservices.io/patterns/communication-style/idempotent-consumer.html [doc]
- IDM-04 (major) Record the idempotency key atomically with the mutation (one transaction); a key saved without the effect, or the effect without the key, is a bug. Check: key insert outside the business transaction. Src: https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter [3p]
- IDM-05 (major) Assume at-least-once delivery; design every handler for duplicates and reordering. Check: "exactly once" assumed for a broker. Src: https://microservices.io/patterns/communication-style/idempotent-consumer.html [doc]
- IDM-06 (minor) Prefer natural idempotency: PUT/set-state by key, not increment. Check: `balance = balance + x` on a retried path. Src: https://learn.microsoft.com/en-us/azure/architecture/best-practices/api-implementation [doc]
- IDM-07 (minor) Same key and same parameters return a semantically equivalent response, not "already exists". Check: duplicate returns 409 for a create the client cannot distinguish. Src: https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter [3p]

## TXN - transactions and consistency
- TXN-01 (major) Keep DB transactions short and local: no user interaction, no long loops, no idle-in-transaction; set `idle_in_transaction_session_timeout`/statement timeout. Check: `await` of slow work between BEGIN and COMMIT. Src: https://www.postgresql.org/docs/current/runtime-config-client.html [doc]
- TXN-02 (blocker) No remote call (HTTP, publish, email, payment) inside an open DB transaction. Check: HTTP/broker/SDK call lexically inside `transaction(`/BEGIN..COMMIT. Src: https://microservices.io/patterns/data/transactional-outbox.html [3p]
- TXN-03 (blocker) Dual write: updating the DB and publishing a message/calling another system as two independent steps is forbidden; use a transactional outbox (relay by polling or CDC). Check: `save()` then `publish()` in the same flow with no outbox row. Src: https://microservices.io/patterns/data/transactional-outbox.html [doc]
- TXN-04 (major) Outbox relay delivers at least once, in order per aggregate; consumers dedupe (inbox/IDM-03). Check: relay without published marker; consumer without dedup. Src: https://microservices.io/patterns/data/transactional-outbox.html [doc]
- TXN-05 (major) Cross-service business transactions use a saga (local transactions + compensations); choreography for few steps, orchestration when the flow grows; no 2PC across services. Check: distributed transaction/XA; multi-service flow with no failure path. Src: https://microservices.io/patterns/data/saga.html [doc]
- TXN-06 (major) Compensating actions are idempotent, retryable, recorded, and business-aware; irreversible steps come last; stuck sagas alert. Check: compensation that assumes a single run or restores a snapshot. Src: https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction [doc]
- TXN-07 (major) Sagas lack isolation: use countermeasures (semantic locks, commutative updates, re-reads, status flags such as PENDING). Check: reading half-finished saga data as final. Src: https://microservices.io/patterns/data/saga.html [doc]
- TXN-08 (major) Isolation level chosen per operation; know Read Committed allows nonrepeatable/phantom reads; Repeatable Read/Serializable must catch SQLSTATE 40001 and retry the whole transaction. Check: serializable without retry loop; read-then-write on Read Committed with no lock/constraint. Src: https://www.postgresql.org/docs/current/transaction-iso.html [doc]
- TXN-09 (major) Read-modify-write on contended rows uses optimistic locking (version column, `UPDATE ... WHERE version = ?`, check affected rows) or pessimistic `SELECT ... FOR UPDATE`; never plain read then write. Check: `SELECT` then `UPDATE` of the same row without version/lock. Src: https://www.postgresql.org/docs/current/explicit-locking.html [doc]
- TXN-10 (minor) Use CQRS/event-sourcing projections only with eventual-consistency UX handled; see DAT rules. Check: read-your-writes assumptions on a projection. Src: https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs [doc]

## LCK - locks and concurrency
- LCK-01 (major) Prefer DB constraints (unique index, check, FK) and optimistic concurrency over explicit locks; catch the violation and handle it. Check: app-level "exists then insert" race. Src: https://www.postgresql.org/docs/current/transaction-iso.html [doc]
- LCK-02 (major) Every explicit lock wait is bounded: set `lock_timeout` (or `NOWAIT`/`SKIP LOCKED`) around `FOR UPDATE`/advisory locks; unbounded waits stall pools. Check: `FOR UPDATE` without `lock_timeout`/`NOWAIT`/`SKIP LOCKED` in scope. Src: https://www.postgresql.org/docs/current/runtime-config-client.html [doc]
- LCK-03 (major) Acquire multiple locks in a consistent global order; retry on deadlock abort. Check: two code paths locking rows A,B in opposite orders. Src: https://www.postgresql.org/docs/current/explicit-locking.html [doc]
- LCK-04 (minor) Advisory locks: prefer transaction-level (`pg_advisory_xact_lock`) so they release automatically; session-level locks must be released explicitly. Check: `pg_advisory_lock` without unlock in `finally`. Src: https://www.postgresql.org/docs/current/explicit-locking.html [doc]
- LCK-05 (blocker) A distributed lock protecting correctness (not just efficiency) needs a lease plus a fencing token checked by the protected resource; Redis `SET NX PX` or Redlock alone does not give it. Check: `SET ... NX` lock guarding writes with no monotonic token verified by the store. Src: https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html [doc]
- LCK-06 (minor) Efficiency-only locks (avoid duplicate work) may use a simple single-node lock; document that it is approximate. Check: lock comment states purpose. Src: https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html [doc]
- LCK-07 (major) No polling/`setTimeout` spin-locks or sleep-based mutual exclusion; use real primitives (DB row lock, queue with single consumer per key, lease service). Check: loops that poll a flag then set it. Src: https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html [3p]
- LCK-08 (minor) Job queues take work with `FOR UPDATE SKIP LOCKED` instead of a shared lock. Check: workers contending on one lock row. Src: https://www.postgresql.org/docs/current/sql-select.html [doc]

## MSG - messaging and events
- MSG-01 (major) Distinguish command (a request to act, with an intended recipient) from event (notification that something happened; sender expects no reply); name accordingly and never style a command as an event. Check: events named `DoX`, commands broadcast. Src: https://martinfowler.com/articles/201701-event-driven.html [3p]
- MSG-02 (major) Schema evolution: additive changes, tolerant readers, version field, upcasting; no breaking change without a new version. Check: removed/renamed event fields. Src: https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing [doc]
- MSG-03 (major) Ordering is guaranteed only per key/partition; partition by aggregate ID and do not assume global order. Check: consumers assuming cross-key order. Src: https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing [doc]
- MSG-04 (major) Dead-letter queue with alerting and a replay procedure; bounded redelivery; poison messages cannot block the partition. Check: infinite requeue; DLQ without alarm. Src: https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction [doc]
- MSG-05 (minor) Event-carried state transfer when consumers need data without calling back; notification-only events when consumers can fetch. Pick deliberately. Check: consumers synchronously calling the producer per event. Src: https://martinfowler.com/articles/201701-event-driven.html [3p]
- MSG-06 (minor) Prevent event loops: handling an event must not trigger an event that re-triggers it. Check: handler publishing the event type it consumes. Src: https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing [doc]

## DAT - data and API
- DAT-01 (major) List endpoints are paginated (limit/offset with sensible defaults) with an enforced maximum page size. Check: `findAll()` returned to clients; no `limit`. Src: https://learn.microsoft.com/en-us/azure/architecture/best-practices/api-design [doc]
- DAT-02 (major) Public APIs are versioned and evolve additively (adding fields is non-breaking; removing/renaming fields is breaking). Check: breaking change on an unversioned route. Src: https://learn.microsoft.com/en-us/azure/architecture/best-practices/api-design [doc]
- DAT-03 (major) CQRS only when read and write models genuinely diverge (different shape, scale, security); simple CRUD does not qualify. Check: separate read store for a table with identical read/write shape. Src: https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs [doc]
- DAT-04 (major) Separate read stores are fed by outbox/events and idempotent projections; staleness is handled in the UX. Check: projection updated by dual write. Src: https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs [doc]
- DAT-05 (major) Event sourcing only for auditability/replay/intent needs; accept snapshots, upcasting, GDPR design; not for CRUD or prototypes. Check: event store with no stated audit/replay requirement. Src: https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing [doc]
- DAT-06 (major) Caching: cache-aside with a defined expiration policy; update the data store, then invalidate the cached item; the cache can be stale, so the data store stays authoritative. Check: cache without TTL; write path not invalidating. Src: https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside [doc]
- DAT-07 (minor) Schema/interface changes follow parallel change (expand, migrate, contract). Check: column drop/rename in the same release as the code change. Src: https://martinfowler.com/bliki/ParallelChange.html [3p]

## OBS - observability and security basics
- OBS-01 (major) Logs carry an interaction/correlation ID; no secrets or PII in logs. Check: `console.log` of request bodies/tokens; logs without request ID. Src: https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html [doc]
- OBS-02 (blocker) No secrets in source or config committed to the repo; load from environment/secret store. Check: grep keys/tokens/passwords in diff. Src: https://12factor.net/config [doc]
- OBS-03 (major) Reject unauthorized requests at the gateway, and enforce access again in each service for its protected operations, including internal calls (gateway checks alone don't authorize downstream operations). Check: service endpoints without authz checks. Src: https://cheatsheetseries.owasp.org/cheatsheets/Microservices_Security_Cheat_Sheet.html [doc]
- OBS-04 (minor) Health/metrics endpoints are not publicly exposed with sensitive detail. Check: `/health` returning dependency internals unauthenticated. Src: https://learn.microsoft.com/en-us/azure/architecture/patterns/health-endpoint-monitoring [doc]
